# segv.sh

[English](README.md) | 日本語

segv.sh は、1:1 とグループでテキストと画像をやり取りする、エンドツーエンド暗号化（E2EE）の Web メッセンジャーです。
鍵はブラウザの中でパスキー（WebAuthn PRF 拡張）によって解錠されます。パスキーかリカバリーコードがあれば、どの端末からでも、
すべての会話とその履歴を復元できます。

サーバーは公開されている前提で設計しています。保存された会話のデータは誰でも読めるので、そこに秘密は何も置きません。
クライアントは自分宛ての行のラベルを計算し、その行だけを取得します。例外は任意の機能で、通知を提供する配備は、通知を有効に
した端末ごとに封をした登録を保存し、それは公開しません（[通知](#通知)を参照）。

このリポジトリのコードが <https://segv.sh> で動いています。

> **状態：実験的なソフトウェアです。** プロトコルと実装は、第三者によるセキュリティレビューを受けていません。使う前に
> [セキュリティモデル](#セキュリティモデル)を読んでください。

## できること

- 1:1 とグループ（最大 32 人）の会話。テキストと画像を送れます。
- パスキーでサインイン。登録時に一度だけ表示されるリカバリーコードでも解錠でき、パスキーは後から追加できます。
- どの端末でも復元：パスキーかリカバリーコードだけで、すべての会話と、メンバー変更より前のものを含む履歴が戻ります。
- メンバーの追加・削除と退出。退出のあと、残ったメンバーは新しい鍵に移ります。
- アカウントごとの指紋。鍵を別の経路で照合するのに使います。
- サーバーがデータを書き換えたり巻き戻したりしたとき、送信者の行の列から行が抜けたとき、メンバーごとに違う内容を見せたときの
  整合性の警告。
- 通知（Web Push）。任意で、既定はオフ、端末ごとに有効にします。通知の文面は「new messages」か、その端末で選べば
  会話名、または会話名と最新のメッセージです（端末が自分で復号します）。招待・リクエスト・リアクションでは通知しません。
- 会話ごとの URL（`/#c/…`）。リンク・リロード・通知からその会話を開けます。`#` 以降はサーバーに送られず、会話の秘密の
  ID でもありません。
- アプリとしてインストールできます（Web アプリマニフェスト。iPhone と iPad では「ホーム画面に追加」）。

## 仕組み

会話のデータはすべて、公開の、作成のみ（書き換え不可）の保存領域に **行** として置かれます。

```
(era, label) → (time, size class, ciphertext)
```

- **era** は 1 週間の区切りです。**ラベル** は、その行を読むべき人だけが計算できる 16 バイト（PRF 出力）です。時刻は Δ 秒
  （本番は 10 秒）に丸められ、暗号文は 4 種類の固定長のどれかです。
- ラベルへの最初の書き込みが勝ち、二度と変わりません。行について他には何も保存しません。送信者・受信者・会話・エポック・
  連番・到着順・IP アドレスはどこにも残りません。
- クライアントは自分が受け取るはずのラベルを計算し、その行だけをキーで取得します。新しい行は、サーバーが保存しない
  WebSocket のトピックで届きます。他人宛てのデータをダウンロードしたり走査したりはしません。例外は、全員が試行復号する
  グローバル受信箱の招待（初めての連絡）だけです。

仕様ではこの設計を Label-Indexed Store と呼んでいます。この上に次のものがあります。

- **アカウント**：アカウントの根は 32 バイトの乱数のアカウント鍵（AK）です。AK は、各パスキーの PRF 出力から導いた X-Wing 鍵と、
  リカバリーコードから導いた X-Wing 鍵に封緘され、そのラップは公開ディレクトリに置かれます。AK はメモリにだけ置きます。
  「この端末を記憶」を選んだときだけ、取り出し不可の WebCrypto 鍵で包んで IndexedDB に保存します。
- **会話**：1:1 もグループも同じプロトコルです。会話はエポックの列で、エポックごとに新しい乱数のエポック鍵を作り、X-Wing
  （X25519 + ML-KEM-768）で各メンバーに届けます。メッセージは Ed25519 で署名してから XChaCha20-Poly1305 で暗号化します。
  メンバー変更は制御レーンに書く署名付きのクレームで、全メンバーが同じ規則で判定します。
- **端末間の状態**：参加している会話、そのエポック鍵、各レーンをどこまで処理したか、連絡先と固定した鍵は、暗号化した
  「自分のレーン」に追記されます。このレーンは自分のアカウントにしか見つけられず、読めません。
- **画像**：ブラウザで再エンコードして EXIF や位置情報を取り除き、ランダムな鍵で暗号化し、パディングしてから、暗号文の
  ハッシュをキーに R2 へ保存します。鍵はメッセージの中にだけ入ります。

### なぜ Double Ratchet や MLS を使わないのか

パスキーだけで新しい端末に全履歴を復元できるなら、パスキーの PRF 出力と公開データだけで、その履歴を読めることになります。
これはプロトコルに依らないので、この目標のもとでは前方秘匿性は得られません。また、同期パスキーはどの端末でも同じ PRF 出力を
返すので端末を区別できず、ラチェットの状態を端末間で同期する必要が出て、同じ問題に戻るうえに鍵や nonce の再利用の危険も
生まれます。さらに、データがすべて公開なので、誰でも保存しておいて将来の量子計算機で解読できます。ここでは前方秘匿性より
耐量子の鍵配送のほうが効きます。詳しい理由は [docs/DESIGN.md](docs/DESIGN.md) の §1 にあります。

## 現状

今の実装はプロトコル v2 の stage 1 です。動くもの：

- パスキーでの登録と、パスキーかリカバリーコードでのサインイン
- 1:1 とグループの会話（テキストと画像）
- リロードや別端末での復元（以前のエポックの履歴を含む）
- メンバーの追加・削除、退出、退出後の鍵の更新
- 整合性チェック：署名付きのチェックポイントの鎖、書き込みの受領証、行の欠落の検知、スプリットビューの検知
- 招待リンク（クライアントのエンジン内部の操作で、UI はまだありません）

まだ無いもの：

- 自分のレーンのスナップショット（[PROTOCOL.md §7.4](docs/PROTOCOL.md#74-snapshots)）。これが無いので、復元は
  アカウントの自分のレーンを最初から読みます。アカウントの履歴が増えるほど、復元に時間がかかります。
- 後の stage で予定しているもの。古い era の R2 へのページ化、匿名の書き込みトークン、OHTTP、33 人以上のグループ、包含証明
  など（[PROTOCOL.md §14](docs/PROTOCOL.md#14-deferred-to-stage-2--3)）。

## セキュリティモデル

プロトコルは 3 種類の攻撃者を想定しています。保存された全バイトを読んで永久に保存し、将来は量子計算機を持ちうる **公開の
読み手**。サーバーを運営し、すべてのリクエストをその場で見て、任意のサーバーコードを動かせるが、暗号は破れない **運営者**。
そして会話の **悪意あるメンバー** です。

保証すること：

- **機密性（将来の量子計算機に対しても）**：メッセージ本文・画像・会話名・メンバー一覧は、メンバーのパスキーの PRF 出力・
  リカバリーコード・アカウント鍵、またはエポック鍵が無ければ読めません。鍵はすべて X-Wing で配送し、それ以外は 256 ビットの
  対称暗号です。
- **公開データからの結び付け不可能性**：行には送信者・受信者・会話が載らず、ラベルは独立な PRF 出力です。公開データから
  分かるのは、各行の era・丸めた時刻・サイズクラス、受信箱の時間枠ごとの件数、ハンドルと公開鍵のディレクトリ、1 時間に 1 回
  「画像か鍵束がアップロードされたかどうか」だけです。
- **招待の匿名性**：初めての連絡の招待が誰宛てかは、量子計算機を使っても公開データから分かりません。
- **メンバー間の真正性**：すべての行は送信者が暗号化の内側で署名します。別のスロット・era・エポック・会話へのリプレイは
  失敗します。
- **前方排除**：削除されたメンバーは以降のエポックを読めず、誰が追加されたかも分かりません（以前のメンバーのうち誰が残ったかは
  分かります）。
- **メンバー変更の生存性**：ゴミの行でメンバー変更が止まることはありません。不正な変更に署名したメンバーはまだ止められますが、
  警告で名指しされ、全メンバーが同じ判定に至ります。
- **可搬性**：パスキーかリカバリーコードがあれば、どの端末でもすべてを復元できます。
- **サーバーの不正の部分的な検知**：行の書き換え、送信者の行の列からの欠落、履歴の書き換えや巻き戻し（各ブラウザが保存する
  署名付きのチェックポイントの鎖による）、メンバー間のスプリットビュー。署名付きの受領証は、書き込みが受け付けられたことを
  証明します。
- データベースが漏れても新たに分かることはありません。会話のデータは最初から公開だからです。公開しない唯一の保存領域である
  任意の通知の登録は、サーバーの鍵で封をしてあり、アカウント・会話・アドレスを含みません。

保証しないこと：

- **運営者は社会グラフを知ります**：各接続が購読するトピック、各クライアントが取得するラベル、すべての書き込みの IP アドレス、
  ディレクトリ検索のプレフィックス。これを隠すには OHTTP や PIR（秘匿情報検索）が必要で、後の stage で予定しています。
- **運営者は行を省いたり、メンバーごとに違う答えを返したりできます**（行・アップロード・ディレクトリのどれについても）。
  上に挙げたとおり一部は検知できますが、証明はできません。包含証明やウィットネスはまだありません。
- **鍵の漏洩**：前方秘匿性はありません。パスキーの PRF 出力（たとえばパスキーを同期しているクラウドアカウントの乗っ取りで）、
  リカバリーコード、アカウント鍵のどれかを得た人は、そのアカウントが読めたすべてを永久に読めます。エポック内の侵害後の回復
  （PCS）もありません。
- **悪意ある JavaScript**：運営者が配信するコード、XSS、侵害された依存パッケージは、次の解錠のときに PRF 出力を抜き取れます。
  これは E2EE の Web アプリに共通の限界です。segv.sh は厳しい Content Security Policy（Trusted Types、外部スクリプトなし）で
  範囲を狭めています。配信コードの透明性は今後の課題です。
- **悪意あるメンバー**：会話全体のメンバー変更を止められます（名指しされます。その変更が誰かを削除していた場合は、その会話の
  メッセージも止まります）。スパムもできます。
- **受信箱を埋める攻撃**：Proof of Work を払えば誰でもグローバル受信箱の 1 日の上限を埋められ、全員の初めての連絡と受信箱経由の
  配送が遅れます。
- **運営者によるディレクトリの鍵のすり替え**：検知できるのは、指紋の照合、固定した鍵、会話に載った鍵との食い違いだけです。
- メンバー間の否認可能性、削除（公開データは消えません）、検閲耐性、耐量子の署名（署名は Ed25519）。
- **通知を有効にした端末について分かること**：[通知](#通知)を参照。

### 通知

通知は、配備が設定し、かつ利用者が端末ごとに有効にしない限りオフです。有効にした端末は、承諾した会話ごとに「呼び鈴」を
登録します。呼び鈴はその会話のエポック鍵から導出する値で、メンバーなら誰でも計算でき、それ以外の人には計算できません。
テキストか画像を送ったクライアントは、ほかのメンバーの呼び鈴を鳴らすようサーバーに頼みます。サーバーは登録された端末に、
中身のない決まった通知を、1 分に 1 回までの頻度で送ります。

- サーバーが端末ごとに保存するのは、サーバーの鍵で封をしたプッシュの宛先と鍵、呼び鈴の鍵付きハッシュ、最後に登録した日だけ
  です。アカウント・会話・トピック・アドレスも、メッセージがどの端末に届いたかも保存しません。登録の変更は 1 日 1 回だけ
  書き込みます。基盤が保存領域の履歴を 30 日間保持するためです。それでも、変更の少ない日には、同じ日に変わった端末どうしが
  推測できることがあります。
- ブラウザのプッシュ事業者（iPhone と iPad の Web アプリはすべて Apple、ほかは Google・Mozilla・Microsoft）は、その端末が
  segv.sh を使っていることと通知の時刻を知り、時刻から同じ会話にいる端末を推測できます。
- 運営者は、鳴らすたびに、そのメッセージがどの端末宛てかを知ります。オフラインの端末も含みます。
- メンバーは、ほかのメンバーの端末に通知を出させる（1 分に 1 回まで）ことや、呼び鈴の登録枠を埋めて通知を妨げることが
  できます。

規範となる記述は [docs/PROTOCOL.md](docs/PROTOCOL.md) の §9.8、§10.10、§11.13、§13.4 です。

プロトコル v2 は、全クライアントが公開ログ全体をダウンロードしていた以前の設計（v1）を置き換えたものです。v2 では
クライアントのコストが他人のデータ量に依存しなくなった代わりに、v1 にあった保証の一部を手放しています。保証すること・しない
こと、v1 より弱くなった点・強くなった点は [docs/DESIGN.md](docs/DESIGN.md) の §3 にすべて挙げています。規範となる記述は
[docs/PROTOCOL.md](docs/PROTOCOL.md) の §0.3–§0.4 と §13 です。

## アーキテクチャ

アプリは Qwik v2 のサイトで、クライアントのエンジンはすべてブラウザの中で動きます。配信は 1 つの Cloudflare Worker です。

| 部品                  | 役割                                                                                                                                                                        |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker                | `/api/v2/*` のバイナリ・JSON API とリアルタイムの WebSocket。ホストの固定、Proof of Work の検査、IP 単位のレート制限（IP は保存しない）。アプリのサーバーサイドレンダリング |
| `ShardDO`（era ごと） | 行の保存。作成のみ、Δ 秒ごとのバッチとハッシュチェーン、era の終わりに封印                                                                                                  |
| `InboxDO`（era ごと） | 初めての連絡に使うグローバル受信箱。クライアントは直近 4 era を読む                                                                                                         |
| `BlobRegDO`           | R2 へのアップロードとその時刻の登録。メンバー変更の判定に使う                                                                                                               |
| `RealtimeDO`          | Hibernation 対応の WebSocket。各クライアントが購読したトピックに新しい行を流す                                                                                              |
| `CheckpointDO`        | 60 秒ごとに、シャード・受信箱・アップロードの登録・ディレクトリの先頭を署名付きのチェックポイントの鎖にする                                                                 |
| `PushDO`（任意）      | 通知を有効にした端末の、封をした登録と、通知の送信。書き込みは 1 日 1 回                                                                                                    |
| D1                    | ディレクトリ（ハンドル ↔ アカウント ID ↔ 公開鍵、鍵のラップ）と、そのハッシュチェーンの公開ログ                                                                             |
| R2                    | 暗号化した画像と鍵束（内容アドレス、immutable）                                                                                                                             |

サーバーにはセッションもログイン状態もありません。サインインとは、ブラウザの中で鍵を解錠することです。書き込みは匿名で、
乱用は Proof of Work（保存させるバイト数に比例）と IP 単位のレート制限で抑えます。

使っているもの：TypeScript、[Qwik](https://qwik.dev/) v2（リリース候補版）、Vite+（`vite-plus`）、Cloudflare Workers、
Durable Objects（SQLite）、D1、R2。暗号はすべて [noble](https://paulmillr.com/noble/) のライブラリ（`@noble/curves`、
`@noble/post-quantum`（X-Wing）、`@noble/ciphers`、`@noble/hashes`）です。

## はじめかた

Node.js 22.18 以降・24.11 以降・26 以降のどれかと、パスキーの保存先が WebAuthn PRF 拡張に対応したブラウザが必要です。PRF に
対応していなくても、リカバリーコードでなら解錠できます。

```bash
npm install
# ローカルのサーバー秘密鍵：32 バイトの乱数 2 つを base64url で（このファイルは gitignore 済み）
node -e 'const k = () => require("node:crypto").randomBytes(32).toString("base64url"); console.log(`ROUTE_KEY=${k()}\nSRV_KEY=${k()}`)' > .dev.vars
npm run db:migrate:local
npm run dev
```

`npm run dev` が表示するローカルの URL を開きます。開発中のパスキーの RP ID は `localhost` です。詳しくは
[docs/DEVELOPMENT.md](docs/DEVELOPMENT.md)（英語）を見てください。

## チェックとテスト

```bash
npm run check                    # 整形と lint
npx tsc --noEmit -p .            # 型チェック：アプリ
npx tsc --noEmit -p test/engine  # 型チェック：エンジンのテスト
npx tsc --noEmit -p test/worker  # 型チェック：Workers ランタイムのテスト
npm test                         # 単体・Workers ランタイム・エンジンのテスト
npm run build                    # 本番ビルド（型チェックと lint を含む）
npm run test:e2e                 # 本番ビルド + wrangler dev + ヘッドレス Chromium
```

E2E テストには Playwright の Chromium が要ります（`npx playwright install chromium`）。E2E テストは専用のローカル状態で、
低い Proof of Work と生成した秘密鍵を使って動くので、開発用のデータには触れません。

## デプロイ

D1 データベース・R2 バケット・秘密鍵・ドメインを用意すれば、`npm run deploy` で Cloudflare にデプロイできます。手順は
[docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)（英語）にあります。後から変えられない選択があります。

- **最初のユーザーが登録する前にドメインを確定させること。** パスキーと PRF 出力はドメイン（WebAuthn の RP ID）に
  紐づくので、後からドメインを変えると全員が鍵を失います。
- **`DELTA_S` と `INBOX_SLOT_S` はデプロイの定数です。** データを保存し始めたら、二度と変えてはいけません。
- **`SRV_KEY` と `ROUTE_KEY` はデプロイの間ずっと同じものを使うこと。** 全クライアントがサーバーの署名鍵を固定していて、
  変わると警告します。

ステージングは、Worker 名・D1 データベース・R2 バケット・秘密鍵・ホスト名をすべて分けた別のデプロイとして動かします。
