# segv.sh 設計メモ

segv.sh は「パスキーでログインし、パスキーに紐づいた鍵で 1:1 / グループの E2EE メッセージ（テキスト・画像）を送る」Web アプリ。
**サーバーの中身はすべて公開**（誰でもいつでも全行を読める）という前提で、クライアントは公開ログ全体を取得し、自分宛ての行だけをローカルで見つけて復号する。

バイト単位の仕様は [PROTOCOL.md](./PROTOCOL.md)。この文書は「なぜそうしたか」と「何を保証し、何を保証しないか」。

---

## 1. 最初の案（PRF → 鍵、1:1 は DH Ratchet、グループは MLS）を疑った結果

結論から言うと、**この前提（全データ公開・パスキーだけでどの端末でも履歴が読める）では、Double Ratchet / MLS は主目的の保証を出せず、複雑さだけが増える**。MVP では 1:1 とグループを同じ 1 つのプロトコル（会話ごとのエポック鍵 + 耐量子ハイブリッド KEM で配送）にした。

### 1.1 「パスキーだけで全履歴」と「前方秘匿性 (FS)」は両立しない

- 新しい端末が持っているのは「パスキー（PRF 出力）」と「公開ログ」だけ。それで全履歴が読めるなら、**PRF 出力 + 公開ログ ⇒ 全履歴** が成り立つ。
- したがって PRF 出力を一度でも盗まれれば（同期パスキーのクラウドアカウント乗っ取り、端末侵害、配信 JS の改ざんなど）、公開ログに永久に残っている過去の全メッセージが読める。これは方式に依らない。
- ラチェットの状態を PRF 由来の鍵で暗号化して公開ログに置けば、古いスナップショットも永久に残るので、FS は見かけだけになる。
- 状態を端末ローカルにだけ持てば FS は出せるが、「別端末でパスキーだけで履歴を読む」ができなくなる（Signal はこちらを選んでいる）。

**どちらを取るかはプロダクトの選択**で、ユーザーの要件（公開ログを検索して自分宛てを読む）は前者なので、segv.sh は「履歴の可搬性」を取り、その代わり FS が無いことを明記する。

### 1.2 同期パスキーは「端末」を区別できない

iCloud キーチェーン / Google パスワードマネージャーの同期パスキーは、全端末で同じ PRF 出力を返す。Double Ratchet は端末ペアごとのセッション（Signal の Sesame 方式の fan-out）、MLS は端末ごとの leaf が必要になり、ここで状態の共有・同期の問題（= 1.1）に戻ってくる。状態を端末間で共有すると鍵・nonce の再利用という致命的な事故も起きうる（RFC 9420 が `reuse_guard` を入れた理由）。

### 1.3 公開ログでの本当の脅威は「今集めて、将来量子計算機で解く」(HNDL)

公開ログは誰でも丸ごと永久保存できる。X25519 だけの Double Ratchet や古典暗号スイートの MLS は、将来の量子計算機で過去ログ全体が読める。**FS より耐量子性のほうが効く**。segv.sh は鍵配送をすべて **X-Wing（X25519 + ML-KEM-768 のハイブリッド KEM）** にしている。

### 1.4 メタデータ

- 「宛先」列を置くと、社会グラフが永久に公開される。segv.sh の行には送信者・受信者・会話 ID が一切載らない。メッセージ行は会話メンバーだけが計算できる 16 バイトの使い捨てタグで識別される。
- MLS は `group_id` / `epoch` を平文で出し、Welcome の `KeyPackageRef` は受信者を特定する。公開 DB で使うには外側をもう一枚包む必要がある。
- 署名を暗号文の外に置くと送信者が公開される。segv.sh は「署名してから暗号化」。

### 1.5 2 つのプロトコルを併用するコスト

Double Ratchet と MLS を両方実装すると攻撃面が倍になる（Matrix の脆弱性の多くは「健全な部品の組み合わせ方」から出た）。ブラウザ向けに保守・監査された Double Ratchet / PQ ラチェット実装も見当たらない（2026-10 時点）。`ts-mls` は X-Wing スイートを持つが未監査の RC。

### 1.6 その他の指摘

- **PRF から直接 ID 鍵を導出しない**。パスキーを複数持てない・ローテーションできない・1 本失うと全部失う。ランダムなアカウント鍵 (AK) を作り、パスキーごとに包む（Bitwarden 方式）。
- **パスワードで包まない**。包んだ blob は公開されるので、オフライン総当たりの標的になる。リカバリーコードは 160 ビット乱数。
- **PRF 対応はまだ不揃い**（Firefox / 一部パスワードマネージャー / 古い Windows Hello は不可、Apple のクロスデバイスで値が変わるバグ報告あり）。リカバリーコードは必須。
- **RP ID（ドメイン）は最初のユーザー登録前に確定させる**。PRF 出力は RP ID に紐づくので、後からドメインを変えると全員が鍵を失う。本番は `segv.sh` 固定。
- **E2EE の Web アプリは配信 JS を信頼するしかない**。サーバー運営者や XSS は次回のパスキー操作時に PRF 出力を抜ける。CSP を厳しくし、外部スクリプトを一切読まない。根本対策（WAICT 等）は将来課題。

## 2. 採用した設計

### 2.1 鍵の階層

```
passkey ──PRF("segv.sh/v1/prf")──▶ prf (32B, 端末内のみ)
                                     │ HKDF(salt=credId)
                                     ▼
                         X-Wing 鍵ペア (パスキーごと) ── 公開鍵で AK を封緘 → 公開ログ (kind 2)
recovery code (160bit) ──HKDF──▶ X-Wing 鍵ペア ─────────── 同上

AK (32B 乱数, アカウントの根) ──HKDF──▶ Ed25519 署名鍵 / X-Wing 受信鍵 / X25519 スキャン鍵
                                         └─ 公開鍵束 (bundle) を自己署名して公開 (kind 1)

会話 conv (16B 秘密) × エポック e ──▶ EK (32B 乱数)
   EK ──HKDF──▶ rk (タグ導出) / mk (メッセージ暗号鍵) / kc (エポック署名へのコミット)
```

- パスキーごとの X-Wing 公開鍵で AK を封緘するので、AK をローテーションするときに全パスキーをその場に揃える必要がない。
- AK は端末のメモリにだけ置く。「この端末を記憶」を選ぶと、取り出し不可 (non-extractable) の WebCrypto 鍵で包んで IndexedDB に置く。

### 2.2 会話（1:1 もグループも同じ）

- 会話は「エポック」の列。エポックごとに新しい乱数 EK を作り、**メンバー全員（自分の他端末向けに自分も含む）へ X-Wing で封緘した招待行 (kind 3)** を出す。
- 招待は宛先を書かない。受信者は全招待行に対して X25519 を 1 回だけ計算して「自分宛てか」を判定し（16B のチェック値）、当たった行だけ X-Wing で開ける。内容の機密性はハイブリッド（X25519 と ML-KEM の両方）、**宛先の判定可能性は古典暗号のみ**（将来の量子計算機は「誰宛ての招待か」は分かるが中身は読めない）。
- メッセージ行 (kind 4) のタグは `HMAC(rk, 送信者インデックス, 連番)`。メンバーは次に来るタグを先に計算して待ち受ける（各送信者 32 個分の窓）。行同士は外部から結び付けられない。
- メンバー変更（追加・削除・退出後の鍵更新）は、旧エポックの「次エポック枠」タグ（`HMAC(rk, "c")`）に変更内容を書いた行（クレーム）と、新メンバー全員分の招待を **1 つのバッチで原子的に** 追加する。ログはタグに UNIQUE 制約があるので、同時に 2 人が変更しても先着 1 つだけが通る（サーバーは会話を知らずに順序づけだけを担う）。
- クレームには変更者の署名が入り、旧エポックの全メンバーが「誰が変更したか」を検証できる。署名の無い・壊れたクレームは無視され（その会話のメンバー変更は以後できなくなるが、会話自体は続く）。
- 既に参加している会話のエポックは **クレームの連鎖に沿ってしか進まない**。番号を飛ばした招待は、「署名付きクレームで自分が削除された後の再追加」以外では拒否する（削除されたメンバーが偽のエポックを差し込んで戻ってくる攻撃を防ぐ）。
- 削除されたメンバーは次エポックの鍵を受け取れないので、以降のメッセージは読めない。古いエポックに後から書き込んでも、その時点のメンバーでなければ受信側が捨てる。
- 鍵ラップには「パスキーの PRF 出力 / リカバリーコードを持つ人にしか計算できない値」を混ぜている。ID と公開鍵は公開なので、これが無いと他人が自分の AK を被害者の ID で登録し、被害者を攻撃者のアカウントにログインさせられてしまう。
- 本文は送信者の Ed25519 で署名してから暗号化。サイズは 256 / 1024 / 4096 / 16384 バイトのいずれかにパディング。

### 2.3 画像

ブラウザでキャンバスに描き直して再エンコード（EXIF・位置情報を除去、最大 2048px、WebP/JPEG）、ランダム鍵で XChaCha20-Poly1305 暗号化、Padmé でサイズを丸めて R2 に保存。ID は暗号文の SHA-256（内容アドレス）。鍵はメッセージ本文の中にだけ入る。

### 2.4 サーバー（Cloudflare Workers）

| 部品                                             | 役割                                                                                                                                                                     |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Durable Object `LogDO`（SQLite, 1 インスタンス） | 権威ある公開ログ。全追記を同期トランザクションで直列化し、連番・ハッシュチェーン・タグ一意性・ハンドル一意性を強制。WebSocket（Hibernation）で全行を全クライアントへ配信 |
| D1                                               | 派生インデックス（ハンドル → 公開鍵束、ID → 鍵ラップ、blob 台帳）。ログから再構築可能                                                                                    |
| R2                                               | 暗号化画像（内容アドレス、immutable キャッシュ）                                                                                                                         |

- 書き込みは匿名。誰が書いたかをサーバーは記録しない。スパム対策は Proof of Work（`x-segv-pow` ヘッダー）と IP 単位のレート制限（IP は保存しない）。
- サーバーにはセッションもログイン状態も無い。「ログイン」はクライアント内での鍵の解錠。
- クライアントはダウンロードした全行のハッシュチェーンを検証し、送信メッセージの中に「自分が見たログ先頭」を入れる。相手のログと食い違えば「スプリットビュー（サーバーが人によって違う履歴を見せている）」として警告する。前回見た位置もローカルに保存し、履歴の書き換え・巻き戻しを検知する。

## 3. 保証すること / しないこと

### 保証する

- メッセージ本文・画像・会話名の機密性。対象は、メンバーのパスキー（PRF 出力）・リカバリーコード・AK・該当エポック鍵のいずれも持たない全員。公開ログを丸ごと保存した**将来の量子計算機を持つ攻撃者も含む**（X25519 と ML-KEM-768 のどちらか一方が安全なら安全）。
- 会話のメンバー構成の秘匿は **古典計算機の攻撃者に対してのみ**（招待の宛先判定が X25519 なので、将来の量子計算機は「どの招待が誰宛てか」＝各エポックのメンバーを知りうる）。
- 送信者の真正性（メンバー間）、改ざん検知、リプレイ拒否。
- 削除されたメンバーは以降のエポックを読めない。
- パスキーだけで、どの端末からでも全履歴を復元できる。
- DB が漏れても問題ない（最初から公開）。

### 保証しない

- **パスキー（または同期先のクラウドアカウント）・リカバリーコード・AK が漏れた場合の前方秘匿性**：その人が参加した全履歴が永久に読める。
- **配信 JS の改ざん**（サーバー運営者、XSS、依存パッケージ）への耐性。
- エポック内の前方秘匿性・侵害後の回復 (PCS)。
- **メタデータの秘匿**：行の時刻・サイズクラス・バッチの形（「会話の作成かメンバー変更が起きて、N 人に鍵が配られた」）は公開。作成とメンバー変更はダミー行で同じ形にしてあるが、その後すぐ同じクライアントが送る 1 行などから推測はできる。WebSocket を見ていれば誰でも書き込み時刻が分かる。サーバー運営者はリクエスト時点で書き込み元 IP、画像を取得した IP（≒画像の受信者）、ログイン時の鍵ラップ検索（≒どのアカウントがどの IP から使われたか）を知りうる。Workers の呼び出しログは無効化しているが、Cloudflare 基盤自体のログは運営者の管理外。運営者だけが見られる blob 台帳（ID・サイズ・アップロード日）がある。トラフィックが少ないうちは時刻相関でかなり推測できる。
- **新しく追加されたメンバーは、それ以前の履歴を検証できない**：招待者が示すメンバー一覧を信じる（招待者が「alice と bob もいる」と嘘をつくと、実際には届かない相手を含む会話に見える）。削除済みメンバーが「将来追加される人」に偽のエポックを先回りして送った場合、本物と偽物の両方を ⚠ 付きの別の会話として表示し、他のメンバーの発言で裏付けられた方から ⚠ が消える（黙ってどちらかを採用はしない）。
- **見知らぬ人からの会話開始を止める仕組み**（承認・ブロック）はまだ無い。誰でも誰とでも会話を始められるので、スパムは受信者の会話一覧と同期時間を増やす。書き込みの Proof of Work は保存させるバイト数に比例して重くしてある。
- メンバー間での否認可能性（署名は第三者に提示できる）。
- 削除・消えるメッセージ（公開ログは追記のみ）。
- 検閲耐性（サーバーは行を拒否・遅延できる。スプリットビューは「検知」のみ）。
- 認証の耐量子性（署名は Ed25519）。
- 内部者による妨害（メンバーは壊れた変更行で会話の以後のメンバー変更を止められる。会話にゴミ行を流して警告を出させることもできる）。

## 4. 今後

1. 「シークレットチャット」モード：端末固定の鍵・履歴の可搬性なし・本物の FS/PCS（X-Wing スイートの MLS か PQ ラチェット）。
2. 端末から端末への履歴移行（パスキーからの復元に頼らない）。
3. AK のローテーションとパスキー失効 UI。
4. Merkle ツリー化したログ + ミラー / 監査人（鍵の透明性）。
5. 配信コードの透明性（WAICT、リリースハッシュの公開）。
6. ML-DSA 署名への移行。
7. 規模が大きくなったら：招待スキャンの高速化（ビュータグ・バケット化）、ログ全量ダウンロードのバケット化。
8. 見知らぬ人からの会話を「リクエスト」として分け、承認・ブロックできるようにする。
9. 招待の宛先判定の耐量子化（ML-KEM ベースのヒント）と、新メンバーがメンバー一覧を相互確認できる仕組み。
