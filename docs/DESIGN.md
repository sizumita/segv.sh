# segv.sh の設計

segv.sh は「パスキーでログインし、パスキーに紐づいた鍵で 1:1 / グループの E2EE メッセージ（テキスト・画像）を送る」Web アプリ。
**サーバーの中身はすべて公開**（誰でもいつでも保存された全バイトを読める）という前提で、クライアントは自分宛ての行のラベルを
自分で計算し、その行だけをキーで取得して復号する（Label-Indexed Store, LIS）。

この文書は「なぜそうしたか」と「何を保証し、何を保証しないか」をまとめる。バイト単位の仕様（規範）は [PROTOCOL.md](./PROTOCOL.md)。
対象はプロトコル v2 の stage 1（現在の実装）で、stage 2 / 3 で加える予定のものは §4 と PROTOCOL.md §14 にある。

## 用語

想定する攻撃者は 3 種類。**P** は保存された全データを読み、永久に保存できる公開の読み手（将来は量子計算機を持ちうる）。**O** は運営者（サーバーとその基盤）で、すべてのリクエストをその場で見て、任意のサーバーコードを動かし、応答を遅らせたり省いたり並べ替えたりできるが、暗号は破れない。**M** は悪意がありうる会話のメンバーで、自分が属するエポックの鍵を持つ。

| 用語             | 意味                                                                                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PRF 出力         | パスキーの WebAuthn PRF 拡張が返す 32 バイトの値。端末の外に出ない                                                                                                                  |
| AK               | アカウント鍵。アカウントの根になる 32 バイトの乱数（§2.1）                                                                                                                          |
| X-Wing           | X25519 と ML-KEM-768 を組み合わせた耐量子ハイブリッド KEM。鍵の配送はすべてこれで行う                                                                                               |
| era (E)          | 1 週間の区切り。行はどれかの era に属する                                                                                                                                           |
| Δ / SKEW         | 行の時刻を丸める秒数（本番 10 秒）と、サーバーの部品間の時計のずれの上限（本番 2 秒）                                                                                               |
| 行・ラベル       | 保存の単位 `(E, label) → (t, cls, body)`。ラベルは、その行を読むべき人だけが計算できる 16 バイト（§2.2）                                                                            |
| レーン           | ラベルの列。会話のエポックごとに各メンバーが書くレーン、メンバー変更を書く制御レーン、アカウントの自分のレーンがある                                                                |
| エポック・EK     | 会話のメンバー構成の 1 世代と、その世代の鍵（エポック鍵）                                                                                                                           |
| D                | エポックの記述子。会話・エポック番号・前の D のハッシュ・メンバー一覧（各メンバーの uid・署名公開鍵・KEM 公開鍵のハッシュ）・会話名を持ち、そのエポックを作った人が署名する（§2.3） |
| 鍵束（SGB2）     | エポックの D などをエポック鍵で暗号化し、継続メンバーそれぞれに EK を封緘したエントリを並べた R2 の blob（§2.3）                                                                    |
| クレーム         | メンバー変更を告げる、制御レーンの署名付きの行（§2.3）                                                                                                                              |
| J                | 会話に参加するのに必要な情報（会話・エポック・EK・鍵束の ID とサイズ）                                                                                                              |
| 受信箱           | 初めての連絡などで J を届ける、全員共通の招待の置き場（era ごと）。誰宛てかは試行復号でしか分からない                                                                               |
| HEADS            | 自分のレーンに記録する、各レーンの処理済みの位置（§2.4）                                                                                                                            |
| チェックポイント | サーバーが 60 秒ごとに署名する、公開データの先頭をつないだ鎖（§2.6, §2.7）                                                                                                          |

## 1. なぜ Double Ratchet / MLS を使わないか

パスキーの PRF 出力から鍵を作り、1:1 は Double Ratchet、グループは MLS を使う、という構成がまず考えられる。
結論から言うと、**この前提（全データ公開・パスキーだけでどの端末でも履歴が読める）では、Double Ratchet / MLS は主目的の保証を出せず、複雑さだけが増える**。segv.sh は 1:1 とグループを同じ 1 つのプロトコル（会話ごとのエポック鍵 + 耐量子ハイブリッド KEM で配送）にした。

### 1.1 「パスキーだけで全履歴」と「前方秘匿性 (FS)」は両立しない

- 新しい端末が持っているのは「パスキー（PRF 出力）」と「公開データ」だけ。それで全履歴が読めるなら、**PRF 出力 + 公開データ ⇒ 全履歴** が成り立つ。
- したがって PRF 出力を一度でも盗まれれば（同期パスキーのクラウドアカウント乗っ取り、端末侵害、配信 JS の改ざんなど）、公開データに永久に残っている過去の全メッセージが読める。これは方式に依らない。
- ラチェットの状態を PRF 由来の鍵で暗号化して公開データに置けば、古いスナップショットも永久に残るので、FS は見かけだけになる。
- 状態を端末ローカルにだけ持てば FS は出せるが、「別端末でパスキーだけで履歴を読む」ができなくなる（Signal はこちらを選んでいる）。

**どちらを取るかはプロダクトの選択**で、segv.sh は「履歴の可搬性」を取り、その代わり FS が無いことを明記する。

### 1.2 同期パスキーは「端末」を区別できない

iCloud キーチェーン / Google パスワードマネージャーの同期パスキーは、全端末で同じ PRF 出力を返す。Double Ratchet は端末ペアごとのセッション（Signal の Sesame 方式の fan-out）、MLS は端末ごとの leaf が必要になり、ここで状態の共有・同期の問題（= 1.1）に戻ってくる。状態を端末間で共有すると鍵・nonce の再利用という致命的な事故も起きうる（RFC 9420 が `reuse_guard` を入れた理由）。

### 1.3 公開データでの本当の脅威は「今集めて、将来量子計算機で解く」(HNDL)

公開データは誰でも丸ごと永久保存できる。X25519 だけの Double Ratchet や古典暗号スイートの MLS は、将来の量子計算機で過去の全データが読める。**FS より耐量子性のほうが効く**。segv.sh は鍵配送をすべて **X-Wing（X25519 + ML-KEM-768 のハイブリッド KEM）** にし、それ以外はすべて 256 ビットの対称暗号にしている。

### 1.4 メタデータ

- 「宛先」列を置くと、社会グラフが永久に公開される。segv.sh の行には送信者・受信者・会話・エポック・連番が一切載らない。行は、その行を読むべき人だけが計算できる 16 バイトのラベル（PRF 出力）で識別される。
- MLS は `group_id` / `epoch` を平文で出し、Welcome の `KeyPackageRef` は受信者を特定する。公開 DB で使うには外側をもう一枚包む必要がある。
- 署名を暗号文の外に置くと送信者が公開される。segv.sh は「署名してから暗号化」。

### 1.5 2 つのプロトコルを併用するコスト

Double Ratchet と MLS を両方実装すると攻撃面が倍になる（Matrix の脆弱性の多くは「健全な部品の組み合わせ方」から出た）。ブラウザ向けに保守・監査された Double Ratchet / PQ ラチェット実装も見当たらない（2026-10 時点）。`ts-mls` は X-Wing スイートを持つが未監査の RC。

### 1.6 その他の設計判断

- **PRF から直接 ID 鍵を導出しない**。パスキーを複数持てない・ローテーションできない・1 本失うと全部失う。ランダムなアカウント鍵 (AK) を作り、パスキーごとに包む（Bitwarden 方式）。
- **パスワードで包まない**。包んだ blob は公開されるので、オフライン総当たりの標的になる。リカバリーコードは 160 ビット乱数。
- **PRF 対応はまだ不揃い**（ブラウザ・OS・パスキーの保存先の組み合わせによる。古い版の Firefox、一部のパスワードマネージャー、古い Windows Hello は不可。Apple のクロスデバイスで値が変わるというバグ報告もある）。リカバリーコードは必須。
- **RP ID（ドメイン）は最初のユーザー登録前に確定させる**。PRF 出力は RP ID に紐づくので、後からドメインを変えると全員が鍵を失う。本番は `segv.sh` 固定。
- **E2EE の Web アプリは配信 JS を信頼するしかない**。サーバー運営者や XSS は次回のパスキー操作時に PRF 出力を抜ける。CSP を厳しくし（Trusted Types を含む）、外部スクリプトを一切読まない。根本対策（WAICT 等）は将来課題。

### 1.7 v1（グローバルなハッシュチェーン）をやめた理由

v1 は segv.sh の最初のプロトコルで、本番にデプロイする前に v2 に置き換えた。v1 は 1 本の公開ログに全行を連番とハッシュチェーンで並べ、**全クライアントが全行をダウンロード**して自分宛てを探していた。改ざん検知は強かったが、コストが利用者全体の量に比例する（O(全体)）。

- 全行のダウンロードと、全招待の試行復号。
- WebSocket で全行を全員に配信。
- 新しい端末・リロードのたびに全履歴を再生。

v2 はこれを「自分宛ての行のラベルを計算して、キーで引く」形に変えた。クライアントのコストは自分の会話・メンバー数・前回記録した位置からの活動量に比例し、他人の量や履歴の長さには依存しない（PROTOCOL.md §11.4）。その代わり、運営者から見た読み出しの秘匿と、グローバルな順序による改ざん検知は弱くなった（§3.3）。

## 2. 採用した設計

### 2.1 鍵の階層

```
passkey ──PRF("segv.sh/v2/prf")──▶ prf (32B, 端末内のみ)
                                     │ HKDF(salt = credId)
                                     ▼
                         X-Wing 鍵ペア (パスキーごと) ── AK を封緘したラップを公開ディレクトリへ
recovery code (160bit) ──HKDF──▶ X-Wing 鍵ペア ─────────── 同上

AK (32B 乱数, アカウントの根) ──HKDF──▶ Ed25519 署名鍵 / X-Wing 受信鍵 / 自分のレーンの鍵 (kS, rS, nS)
                                         └─ 公開鍵束 (bundle) を自己署名してディレクトリへ

会話 conv (16B 秘密) × エポック e ──▶ EK (32B 乱数)
   EK ──HKDF──▶ rk (ラベル導出) / mk (行の暗号鍵) / dk (鍵束の暗号鍵) / kc (エポック署名へのコミット) / nk (トピック)
```

- パスキーごとの X-Wing 公開鍵で AK を封緘するので、AK をローテーションするときに全パスキーをその場に揃える必要がない。
- 鍵ラップには「パスキーの PRF 出力 / リカバリーコードを持つ人にしか計算できない値」を混ぜている。ID と公開鍵は公開なので、これが無いと他人が自分の AK を被害者の ID で登録し、被害者を攻撃者のアカウントにログインさせられてしまう。
- AK は端末のメモリにだけ置く。「この端末を記憶」を選ぶと、取り出し不可 (non-extractable) の WebCrypto 鍵で包んで IndexedDB に置く。

### 2.2 保存の形（行とラベル）

- 会話のデータはすべて **行** `(E, label) → (t, cls, body)` として保存される。`E` は 1 週間の **era**、`label` は 16 バイトの PRF 出力、`t` は Δ 秒（本番 10 秒）に丸めた公開時刻、`cls` はサイズクラス（256 / 1024 / 4096 / 16384）、`body` は固定長の暗号文。
- 行は **作成のみ**：`(E, label)` への最初の書き込みが勝ち、二度と変わらない。行について他には何も保存しない（送信者・受信者・会話・エポック・連番・到着順・IP）。
- クライアントは、自分が受け取るはずの行のラベルを計算してキーで引く。新しい行はラベルとは独立なトピック（会話のエポックごと、自分のレーン、リンク）の WebSocket で受け取る。トピックはどこにも保存されない。
- ラベルの列は **レーン** を作る。会話のエポック e の各メンバーは自分のレーン `Lmsg(ℓ, E, n)` に書き、era ごとに 0 から詰めて書く（密な prefix）。クライアントはレーンの先頭を少数のキーで探り（P0 = 2、ヒットが続けば W = 8 ずつ）、使われていない era は 1 キーで済む。

### 2.3 会話（1:1 もグループも同じ）

- 会話は **エポック** の列。エポックごとに新しい乱数 EK を作り、メンバー一覧を含む記述子 **D**（各メンバーの uid・署名公開鍵・KEM 公開鍵のハッシュと、会話名）を、そのエポックを作った人（会話の作成者、またはメンバー変更をした人）が署名する。D と全員の KEM 公開鍵は、エポック鍵で暗号化して **SGB2 鍵束**（R2 の blob）に入れる。鍵束の各エントリは継続メンバーへの EK の封緘で、**乱数を EK から導出する**（sealDet）ので、EK を得たメンバーは誰でも全エントリを再計算して検証できる。
- 送信は自分のレーンに 1 行。本文は送信者の Ed25519 で署名してから暗号化し、AAD と署名が era・ラベル・会話・エポックを束縛するので、別の場所へのリプレイは失敗する。各行は自分の前の行の位置とハッシュ（`prev` / `prevh`）を持ち、レーンの欠落を検知できる。
- **メンバー変更**（追加・削除・退出後の鍵更新・改名）は、新しい鍵束を R2 に登録してから Δ + SKEW 待ち、旧エポックの **制御レーン** `Lctl(E, k)` の最初の空きスロットに署名付きの **クレーム** を書く。クレームは新しい D のハッシュ・EK のコミット・鍵束の ID とサイズ・`rm`（旧メンバーのうち抜ける人のビット）・各レーンの `cut` を持つ。
- **e-有効性**：クレームが有効なのは、復号・署名（D に載った鍵で検証）・`prevD`・`rm`・`cut` の範囲が正しく、鍵束が **クレームより前の時刻に登録済み** で、形が正しいときだけ。判定は全メンバーが共有する公開の事実だけで行い、ディレクトリには依存しない。ゴミ行・署名の無い行・無効なクレームは無視され、次のスロットが使われる（v1 のように凍結しない）。
- **勝者と確定**：制御レーンで最初の e-有効なクレームが勝者（それより前のスロットがすべて「無効」と決まっていること）。前の era が封印（sealed）されたのを観測したら確定する。全メンバーが同じ勝者に到達する。
- **処理**：勝者のクレームで自分のビットが立っていれば削除（「@x removed you」）。そうでなければ自分のエントリを開き、新しい D と鍵束を検査する。エントリが開かない、または検査が 1 つでも失敗すれば、そのクレームの署名者を名指しした警告とともに **会話全体のメンバー変更が凍結** される（全員が同じ判定になるので、誰かだけが古いエポックに取り残されることはない）。検査が通れば e+1 に移り、旧エポックのレーンを掃き出し（sweep）、まだ e+1 で発言していないメンバーの e のレーンは追い続ける（followed lane）。
- **古いエポックの行**：削除されたメンバーの行は、その削除クレームの保存時刻より前のものだけ受け入れる（同じ Δ バッチ内は cut で決める）。後から知ったクレームでこの判定をやり直し、落ちた行は表示から消える。
- **退出**：退出者は自分のレーンに LEAVE を書いて送信をやめる。残ったメンバーは、退出者が残っているエポックでテキストや画像を送る前に、退出者を外すコミット（鍵の更新）をする。
- **参加**：新しいメンバーには J（会話・エポック・EK・鍵束の ID とサイズ、90 バイト）を届ける。経路は、①条件を満たす 1:1 の会話への WELCOME 行、②グローバルな受信箱（β = 0）への招待（X-Wing の試行復号で見つけるので、宛先判定にタグは無い）、③リンクのハロー。知らない人からの会話は **リクエスト** として分けられ、開くまで通知・購読されない。
- 既に参加している会話のエポックは **クレームの連鎖に沿ってしか進まない**。番号を飛ばした J は、「署名付きクレームで自分が除かれた後の再追加」以外では受け付けない。

### 2.4 自分のレーン（端末間の状態）

アカウントの端末間で共有する状態（参加している会話、エポック鍵、処理済み位置 HEADS、連絡先と鍵のピン、退出、配送の進み具合など）は、AK から導いた鍵で暗号化した **自分のレーン** に追記していく。復元は自分のレーンを読んでから、各会話の制御レーンをたどってエポックを再導出し、HEADS の位置から各レーンを読む。初期表示は最近の 20 会話の各レーン末尾 30 行で、会話を開くと最大 500 件まで遡る。

### 2.5 画像

ブラウザでキャンバスに描き直して再エンコード（EXIF・位置情報を除去、最大 2048px、WebP/JPEG）、ランダム鍵で XChaCha20-Poly1305 暗号化、Padmé でサイズを丸めて R2 に保存。ID は暗号文の SHA-256（内容アドレス）。鍵はメッセージ本文の中にだけ入る。

### 2.6 サーバー（Cloudflare Workers）

| 部品                                   | 役割                                                                                               |
| -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `ShardDO`（era ごと、stage 1 は 1 つ） | 行の保存。作成のみ、Δ ごとのバッチとハッシュチェーン、era の封印                                   |
| `InboxDO`（era ごと）                  | グローバル受信箱（招待）。スロットごとに確定し、直近 4 era だけ読める                              |
| `BlobRegDO`                            | R2 の blob の登録とその時刻（クレームの e-有効性に使う）                                           |
| `RealtimeDO`                           | WebSocket（Hibernation）。購読したトピックの新しい行だけを流す                                     |
| `CheckpointDO`                         | 60 秒ごとに、シャード・受信箱・blob 登録・ディレクトリの先頭を署名付きのチェックポイントの鎖にする |
| `PushDO`（任意、1 つ）                 | 通知の登録（宛先と鍵を封をして保存、呼び鈴は鍵付きハッシュ）と送信。登録の書き込みは 1 日 1 回     |
| D1                                     | ディレクトリ（ハンドル ↔ uid ↔ 公開鍵束、鍵ラップ）とその公開ログ                                  |
| R2                                     | 暗号化画像と鍵束（内容アドレス、immutable キャッシュ）                                             |

- 書き込みは匿名。誰が書いたかをサーバーは記録しない。スパム対策は Proof of Work（`x-segv-pow` ヘッダー、保存させるバイト数に比例）と IP 単位のレート制限（IP は保存しない）。
- サーバーにはセッションもログイン状態も無い。「ログイン」はクライアント内での鍵の解錠。

### 2.7 整合性の検知

- 一度見た行の本文・時刻・クラスが変われば「書き換えられた」と警告する。
- レーンの `prev` / `prevh` で欠落を検知する（穴の向こうの行も、`prev` をたどって検証してから表示する）。
- 書き込みには署名付きの受領証が返り、クライアントが検証する。
- チェックポイントの鎖をブラウザごとに保存し、巻き戻し・書き換えを検知する。
- 各行に「送信者が検証した最新のチェックポイント」の参照（16 バイト）を入れ、メンバー間で鎖が分岐していれば「スプリットビュー」と警告する。

どれも致命的な停止にはせず、消えない重大警告として表示し、メッセージのやり取りは続ける。

### 2.8 通知（Web Push、任意）

- 配備が `VAPID_SK` と `PUSH_KEY` を設定したときだけ有効。利用者が端末ごとに有効にし、同期しない。既定はオフ。
- 呼び鈴 `B_e(ℓ) = t16(HMAC(nk_e, "segv.sh/v2/bell" ‖ ℓ))`：会話のメンバーなら誰でも計算でき、外部の人と、外されたメンバー（新しいエポックについて）には計算できない。行・自分のレーンの記録・既存 API の形式は変えない。
- 端末は、承諾した会話（リクエストでなく、終了も退出もしておらず、開始者が自分か連絡先）の現在のエポックの自分の呼び鈴を登録する。送信者はテキストか画像を書いたあと、ほかのレーンの呼び鈴（と、新しいエポックでまだ書いていないメンバーの 1 つ前の呼び鈴）を鳴らす。招待・リクエスト・リアクションでは鳴らさない。
- 通知の文面は全端末・全通知で同じ固定文（"new messages"）。端末あたり 1 分に 1 回まで、ゆらぎ付き。
- PushDO は登録だけを保存する（宛先と鍵は `PUSH_KEY` で封、呼び鈴は鍵付きハッシュ、日付は日単位）。鳴らしたことに関する状態はメモリだけ。基盤が保存領域の履歴を 30 日保持するので、変更は UTC の日が終わってから 1 日 1 回のパスでまとめて書き、履歴が日より細かく日付を刻まないようにした。

## 3. 保証すること / しないこと

### 3.1 保証する（stage 1）

- **機密性**：メッセージ本文・画像・会話名・メンバー一覧は、メンバーのパスキー（PRF 出力）・リカバリーコード・AK・該当エポック鍵のいずれも持たない全員に対して秘匿される。公開データを丸ごと保存した**将来の量子計算機を持つ攻撃者も含む**（鍵はすべて X-Wing で配送し、それ以外は 256 ビットの対称暗号）。
- **公開データからの結び付け不可能性**：行には送信者・受信者・会話・エポック・連番が載らず、ラベルは独立な PRF 出力。公開データから分かるのは era、Δ に丸めた時刻、サイズクラス、受信箱のスロットごとの件数、ディレクトリ、1 時間に 1 回「blob が登録されたかどうか」だけ。
- **招待の受信者の匿名性**：受信箱の招待は X-Wing の試行復号で見つけるので、量子計算機に対しても誰宛てか分からない（v1 は古典計算機に対してだけ）。
- **メンバー間の真正性**：全行は送信者が Ed25519 で署名し、AEAD の中に入る。別のスロット・era・エポック・会話へのリプレイは失敗する。
- **前方排除**：削除されたメンバーは以降のエポックを読めず、誰が追加されたかも分からない（新しい D は新しいエポック鍵で暗号化される）。旧メンバーのうち誰が残ったかは、クレームの `rm` で分かる。
- **メンバー変更の生存性**：ゴミ行・署名の無い行・無効なクレームでメンバー変更が止まることはない。e-有効なクレームに署名したメンバーはまだ止められるが、名指しされ、全員が同じ判定になる（その凍結が誰かを削除していた場合は、その会話でのテキスト・画像も止まる）。有効性はディレクトリに依存しない。
- **可搬性**：パスキーかリカバリーコードだけで、どの端末からでも全会話と全履歴を復元できる。コストは会話数・メンバー数・前回のスナップショット以降のエポック・前回 HEADS を記録してからの活動に比例し、履歴の長さには依存しない。
- **サーバーの不正の（部分的な）検知**：§2.7 のとおり。
- 会話データの DB が漏れても問題ない（最初から公開）。公開しない唯一の保存は任意の通知の登録（PushDO）で、`PUSH_KEY` で封をし、アカウント・会話・トピック・IP を含まない。

### 3.2 保証しない（stage 1）

- **運営者 (O) は社会グラフを知る**：各 WebSocket のトピック集合、各キーの検索、書き込み元 IP、ディレクトリ検索のプレフィックス。隠すには OHTTP / PIR が要る（stage 2/3）。
- **運営者は行を選んで隠したり、メンバーごとに違う答え**（blob 登録やディレクトリについても）を返したりでき、stage 1 のクライアントはそれを証明できない（包含証明・ウィットネスが無い）。
- **パスキー（または同期先のクラウドアカウント）・リカバリーコード・AK が漏れた場合の前方秘匿性**：その人が参加した全履歴が永久に読める。エポック内の前方秘匿性・侵害後の回復 (PCS) も無い。
- メンバー間での否認可能性（署名は第三者に提示できる）。削除（公開データは消えない）。検閲耐性。
- **配信 JS の改ざん**（サーバー運営者、XSS、依存パッケージ）への耐性。
- 使えないクレームに署名して会話全体のメンバー変更を（名指しされつつ）止める、またはスパムする悪意あるメンバー。
- グローバル受信箱の 1 日の上限を埋め続ける者（初めての連絡と受信箱経由の配送を全員について遅らせる）。
- 運営者によるディレクトリの鍵のすり替え（検知できるのは、指紋の比較、CONTACT / MEMBER のピン、会話の D に載った鍵との食い違いだけ）。
- 認証の耐量子性（署名は Ed25519）。
- **通知を有効にした端末について**（§2.8）：プッシュ事業者 (N) は端末と通知の時刻を知り、時刻から会話の共有を推測できる。運営者は鳴らすたびに宛先の端末（オフラインのものも）を知る。保存履歴（30 日）からは、変更の少ない日に同じ日に変わった端末どうしが推測できる。メンバーは通知を出させる（1 分に 1 回まで）ことも、呼び鈴の枠を埋めて妨げることもできる。

### 3.3 v1 より弱くなった点

v1 より弱くなった点は、ここにすべて挙げた。どれも意図した取引で、stage 2 / 3 で対処する予定。

1. **運営者に対する読み出しの秘匿**：v1 は全クライアントが全行をダウンロードし、WebSocket は全行を全員に流していたので、運営者には誰がどの会話を読んでいるか分からなかった。stage 1 は各クライアントが求めた行だけを返すので、運営者は社会グラフと会話ごとの活動を知る。O(全体) のダウンロードをやめた以上避けられない。
2. **改ざん・欠落の証拠**：v1 のクライアントは処理した全行を覆う 1 本のハッシュチェーンを検証し、飛んだ連番や壊れた鎖は致命的、メッセージ内の先頭ハッシュで 2 人の間の分岐も露見した。stage 1 にはグローバルな順序が無く、包含証明も検証しない。検知は、行の不変性、レーンの `prev` / `prevh`、ブラウザごとに保存したチェックポイントの鎖、メンバー間の `ck16` の比較（読み手のセッションマップより 2 時間以上古いチェックポイントを参照する行は比較されないので、復元やスクロールバックで読んだ履歴は対象外）、受領証に限られる。`prev` / `prevh` の鎖を壊さない選択的な欠落や、一部のメンバーにだけ見せる行は検知できない。整合性の失敗は致命的ではなく、消えない重大警告になった。
3. **ディレクトリの完全性**：v1 では公開鍵束がログの行で、各クライアントが自分でハンドル → uid の対応を作り、鍵のすり替えはログを分岐させた。stage 1 のディレクトリはサーバーが答える D1 で、その公開ログはチェックポイントでコミットされるがクライアントは包含を検証しない。運営者は 1 人のクライアントに対して鍵束をすり替えられる。防御は指紋、CONTACT / MEMBER のピン（最初に検証した答えを保持するので、その時点でのすり替えは以後のセッションでも報告され続ける）、各 D に載った鍵（共有している会話の鍵と食い違えば「the public keys of @x changed」）。逆に、v1 は未登録の uid を含む会話を拒否し、鍵は常にログから取っていたが、stage 1 はそういう会話も受け入れ、鍵は署名された D から取る（有効性がディレクトリに依存しないように）。未登録、またはディレクトリと鍵が違うメンバーは、ハンドルではなく `?…` の不明メンバーとして表示される。作成者やコミッターは本物の uid に偽の鍵を載せられるが、その枠をその人のハンドルで見せることはできない。ただし鍵束のエントリは D に載った鍵へ配られるので、その鍵を持つ者はメンバーが外すまで鍵を受け取り続ける（メンバーが別アカウントを追加するのと同じ力で、ハンドルの代わりに `?…` と表示される点だけが違う）。
4. **クレームの有効性がサーバーの答えに依存する**：e-有効性の規則のうち (g)(h)（PROTOCOL.md §6.4）は、blob の登録と blob 自体についてのサーバーの答えを使う。嘘をつく運営者は 1 つの会話のメンバー間でクレームの判定を食い違わせられる（2 と同じ力と検知可能性）。ディレクトリの答えはもう有効性に影響しない。
5. **招待の保持期間**：v1 はすべての招待を永久に見つけられた。stage 1 のクライアントは直近 4 era（約 4 週間）の受信箱しか読まない。その間に受信者のどの端末も拾わなかった初めての連絡は失われ、招待し直す必要がある。未読のリクエストは 64 件までなので、スパムで本物のリクエストが押し出されうる。参加した会話は自分のレーンに記録され、失われない。
6. **遅延**：メンバー変更と作成は、他の人に見えるまで少なくとも Δ + SKEW（本番 12 秒）待ち、作成者の最初のメッセージもそれを待つ。ハンドルでの初めての連絡は受信箱のスロットとポーリング間隔ぶん遅れる。退出後の最初のメッセージは鍵の更新を待つ。送信ごとに制御レーンの確認の `get` が 1 回増え（v1 の送信前の同期と同じ）、準備や応答が遅いときはもう 1 回増える。
7. **順序**：v1 はサーバーの全順序（連番）で並べた。stage 1 は送信者の時刻（保存時刻 ± 5 分に丸める）で並べるので、同時に送られたメッセージの順序は端末ごとに違いうる。削除クレームを後から知ると、すでに表示した行が取り下げられることがある。
8. **新しい端末での履歴**：v1 は全部を再生した（全履歴がすぐ揃うが O(全体) のコスト）。stage 1 は最近の 20 会話の各レーン末尾 30 行をすぐ表示し、会話を開くと 500 件まで読み込む。それより古い履歴も `prev` でたどれるが、UI に「さらに読み込む」は無い。復元の HEADS より前のエポックの退出状態は読み込んだ行からしか分からないので、退出の LEAVE 行を読むまで、退出者を外したクレームが「削除」に見えたり「@x left」の行が欠けたりしうる。
9. **サイズクラスが 1 つ増えた**：256 クラスが戻った。バイナリ形式ではこれが「普通の」クラス（短いテキスト、画像、退出、WELCOME）なので珍しい行を目立たせはしないが、テキストが 129 バイト以下かどうかは新しく分かる。
10. **ディレクトリ検索がプレフィックスを運営者に漏らす**：v1 はダウンロード済みの全ディレクトリから引いたので、運営者は誰が誰を調べたか分からなかった。stage 1 は検索ごとに `H(handle)` か `H(uid)` の p ビットのプレフィックスを送る（ハンドルの解決、共有メンバーや招待者の最初の検証。結果は MEMBER レコードに残るので、未登録の uid 以外は復元で繰り返さない。コミットは誰も検索しない）。匿名集合は通常 64〜128 アカウントで、クライアントは公開ログの大きさから p を制限する。
11. **第三者が初めての連絡と受信箱経由の配送を遅らせられる**：受信箱には全体で 1 日 2000 件の上限がある。PoW を払って埋め続ける者は、1:1 の無い相手の追加や初めての連絡を翌日まで遅らせられる。カーソルの無い端末は最大 56 000 件の招待を試行復号する必要がある（自分のレーンのカーソルで、通常は前回のポーリング以降だけになる）。
12. **作成・追加と、削除・鍵更新が見分けられる**：v1 はすべての変更と作成を同じ形にして N だけを明かした。stage 1 は N を隠すが、受信箱の招待は公開の行なので、直後に招待が続く変更は「1:1 の無い誰かを招待した」、続かないものは「しなかった」と推測できる。
13. **容量**：era ごとの ShardDO は 1 つで、最大 10 GB（stage 1 の見積もりで約 25 000 人の活動）・約 1000 リクエスト/秒。RealtimeDO と現在の InboxDO も 1 つずつ。シャードが満杯になると次の era まで書き込みが FULL になる。S > 1 は経路制御がすでにあるのでパラメータの変更で済む。
14. **鍵エントリの誤りは全員を凍結し、削除を含む凍結はメッセージも止める**：v1 は招待が届かなかったメンバーだけを凍結した。stage 1 は継続メンバーの全エントリを新しいエポック鍵から導出するので、誰か 1 人のエントリが誤っていれば全員にとって D′ が無効になり、会話全体が凍結される（署名者は名指しされる。どのみち e-有効なクレームに署名できるメンバーは無効な D′ で全員を凍結できるので、攻撃者の力は増えない。代わりに誰も古いエポックに取り残されない）。また、誰かを削除したクレームで凍結された会話では、削除されたメンバーがまだ旧エポックの鍵を持っているので、テキスト・画像を送れない（読み取り専用になり、メンバーは新しい会話を始める）。
15. **古いエポックの行を live で取りこぼしうる**：v1 はグローバルログの全行を処理した。stage 1 は現在のエポックのレーンと、まだ発言していないメンバーの 1 つ前のエポックのレーンだけを追う。他の全員がそのレーンを掃き出した後に古いエポックへ着地した行は live では誰にも表示されず、それより後の HEADS からの復元でも漏れる（スクロールバックだけが見つける）。誠実な単一端末の送信者はこれを起こさない（送信の直前に制御レーンを確認し、遅れた行を再確認する）。残るのは、同じアカウントの端末同士がクレームと競合する場合と、次の鍵束を前もって登録してクレームを 2 つ続けて出す悪意あるメンバーの場合で、どちらもスクロールバックすれば見つかり、後者は全員に見える署名付きクレームを 2 つ要する。

### 3.4 v1 より強くなった点

- **招待の受信者**は量子計算機に対しても隠れる（PQ の試行復号。v1 の X25519 ビュータグは量子計算機には受信者を明かした）。
- **メンバー変更が正確なメンバー数を明かさない**（v1 のバッチは `[4, 3×N]`。stage 1 の鍵束は 8 か 32 のバケットだけで、公開データから鍵束は列挙できない）。
- **削除されたメンバー**は、誰が追加されたかを知らない（`rm` で旧メンバーのうち誰が残ったかは分かる）。
- **ゴミ行でメンバー変更が凍結しない**（v1 はクレームの枠にどんな行が来ても凍結した）。署名付きクレームは今も凍結できるが、署名者が名指しされ、全員が同じ判定になる。
- **凍結した会話で削除されたメンバーが読み続けられない**（v1 は削除を含むクレームで凍結したエポックにも書き込みを続けさせた）。
- **D の有効性がブラウザに依存しない**：v1 は名前が読み手の `validName`（JavaScript エンジンの Unicode のバージョンに従う文字クラスと NFKC）に通らない D を拒否したので、ブラウザによって判定が割れえた。stage 1 は名前の検査を作成時と表示時だけにした。
- **署名の有効性がライブラリに依存しない**：署名鍵を素数位数の部分群に制限し、cofactored の検証式に固定した。
- **バッチが観測できない**：公開データからはグローバルな順序・バッチ・到着順が見えず、時刻は Δ に丸められる。

## 4. 今後（stage 2 / 3）

- **保存と経路**：封印した era を R2 にページ化（`.idx` / `.dat`、マニフェスト、封印済み era の `kroute_E` の公開、古い ShardDO の削除）、ラベル順の公開ページ読み出し、S > 1 のシャード割り当てと緊急分割、鍵束エントリの Range 読み出し。
- **乱用対策と通信路**：匿名の書き込みトークン（VOPRF）と払い戻し、OHTTP と静かなモード、配信の分離と Bloom フィルタによる fan-out、PushDO の分割（呼び鈴の接頭辞でシャード）。
- **受信箱**：ハンドルのプレフィックスに合わせたバケット（β > 0）、動的な価格付け、リンク専用フラグ。
- **グループ**：33 人以上、共有レーン、管理者ポリシー、128 / 512 / 1024 人のバケット、まとめての削除、TreeKEM 型の O(log m) の鍵更新。
- **監査可能性**：ウィットネスと共同署名、行の包含証明、ディレクトリの包含証明、blob 登録のミラーフィード。
- **暗号とアカウント**：ディレクトリと受信箱の PIR、ML-DSA 署名、AK のローテーションと鍵束の版管理（継続メンバーの `kh` を変えるコミットが要る）、AK ローテーション後の遅延した鍵更新、定期的な鍵更新（PCS-lite）。
- **クライアント**：リンク共有の UI とその Engine メソッド、既読位置の同期、ローカルキャッシュ、500 件を超える「さらに読み込む」、遅れた行の確認をすべての送信の後に行う（§3.3 の 15 を閉じる）、「シークレットチャット」（端末固定の鍵・可搬性なし・本物の FS/PCS）、配信コードの透明性（WAICT、リリースハッシュの公開）。
