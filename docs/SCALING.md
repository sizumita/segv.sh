# サーバーをスケールさせる設計（stage 2 の提案）

stage 1 の構成（[DESIGN.md](./DESIGN.md) §2.6、[PROTOCOL.md](./PROTOCOL.md) §9）は、era ごとに 1 つの ShardDO、1 つの RealtimeDO、全員共通の 1 つの受信箱、1 つずつの BlobRegDO / CheckpointDO / PushDO、D1 の 1 本の dirlog でできている。どれも Durable Object 1 個の上限（約 1 000 リクエスト/秒、SQLite 10 GB、ハイバネーション WebSocket 32 768 本、メモリ 128 MB）に突き当たる。

この文書は、PROTOCOL.md §0.3 の保証と §13.1 の漏洩表を**変えずに**水平方向へ伸ばす設計の提案で、採用した部分は PROTOCOL.md に規範として書き直す。数値は PROTOCOL.md の記述と Durable Objects の制限（2026-11 時点）による見積もりで、桁を見るためのもの。

## 0. 要約

- **分割の鍵は全部サーバー秘密の PRF で決まる。** 行はラベル（`v = HMAC(kroute_E, label)`、すでに PROTOCOL.md §4.4 にある）、リアルタイムはトピック、push は呼び鈴と宛先、blob は id。どの境界も P には乱数にしか見えず、O はすでにトピックと IP を見ているので、分割で P の視界も O の視界も増えない。攻撃者は特定のシャードを狙えない。
- **era が移行点。** 行ストアと受信箱のトポロジは era ごとの定数にし、次の era から変える。過去の era のデータは動かさない。封印した era は R2 に移し、DO は空にする。
- **グローバルに 1 つ残るのは低頻度のものだけ。** チェックポイント（毎分）とディレクトリの連番（登録のたび）。どちらも 1 つの DO で足りるが、連番は D1 への楽観的リトライから「1 つの書き手」に変える。
- **受信箱だけはトレードオフ。** 「誰宛てか全ユーザーの中から分からない」は読み手が全招待を試行復号することと表裏一体なので、匿名集合の大きさ K（既定 2^14）を固定し、それ以上のユーザーがいる era からバケットに分ける。それまでは今のまま（β = 0）。バケットの決め方に 2 案あり（§4.3）、どちらにするかは決めてもらう点。
- **クライアントの変更は受信箱まわりだけ**（バケット、通知トピックの購読、ポーリングの退避）。シャードもリアルタイムの分割も Worker の中で閉じる。

## 1. 守るもの

PROTOCOL.md §0.3 と §13.1 を基準にして、増やしてはいけないものを列挙する。§5 で各変更をこの表に照らす。

| 誰に         | いま見えるもの（これ以上増やさない）                                                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P            | era、Δ に丸めた `t`、サイズクラス、受信箱のスロットごとの件数、ディレクトリ、1 時間に 1 回「blob が登録されたか」、チェックポイントの鎖。行に送信者・受信者・会話・エポック・連番は載らず、ラベルは独立 |
| O            | 各ソケットのトピック集合、各クライアントが引いたラベル、書き手の IP、ディレクトリ検索の p ビットのプレフィックス                                                                                        |
| 保存されない | トピック、購読、IP、RESUME のリング、レート制限の鍵、Δ バッチ内の到着順、受信箱のジッター。PushDO の保存は §9.8 の列挙どおりで、変更は日単位でしか履歴に残らない                                        |

## 3. 設計原則

1. **分割鍵は鍵付き PRF。** 攻撃者は特定のシャードを狙えず（ラベルから v を計算できない）、P は分割を会話や人に結び付けられない。
2. **era 単位の定数。** `S_E`（行のシャード数）と `β_E`（受信箱のバケット数の指数）は era ごとの配備パラメータで、`start(E) − SKEW` より前に決めて以後変えない。Δ と同じく各 DO が最初の書き込みで値を固定し、違う値で呼ばれたら例外にする（黙って別のシャードに書くことを防ぐ）。
3. **状態を持たない部品はいつでも変えられる。** ConnDO / FeedDO の数は再接続で収束する（ソケットは 1 時間で張り替わる、§9.4）。
4. **保存先を寿命で分ける。** 書き込み中の era は DO（CAS と Δ バッチの直列化が要る）、封印した era は R2（不変・安い・キャッシュできる）。
5. **グローバルな部品の頻度は「毎分」か「書き込みごとに 1 RPC」以下。**

## 4. 部品ごとの設計

### 4.1 行ストア：`shard/v2/{E}/{i}` × S_E、封印後は R2

**シャード数。** `S_E = 2^{s_E}`、`i = v >> (63 − s_E)`（§4.4 のまま。`shardOf` は実装済み）。`s_E` は配備変数 `SHARD_MAP`（`E_from:s` の列。era E に効くのは `E_from ≤ E` の最後の項）で決め、`/api/v2/era/{E}` と params の `shards` に出す。目安は前の era の実績の 4 倍：`S_E ≥ 4 · bytes_{E−1} / 4 GiB` かつ `S_E ≥ 4 · peak_rps_{E−1} / 1 000` を 2 の冪に切り上げる。空のシャードは費用ゼロなので多めでよい。各 ShardDO は最初の書き込みで `s_E` を `meta` に固定する。

**Worker。** put / get はすでに `(E, shard)` でまとめて RPC している（§10.3 手順 4、§10.4）。変わるのは `SHARD_BITS` が era の関数になることだけ。1 つの get（最大 256 鍵）は最大 `min(256, S_E)` 個の RPC に並列で分かれる。

**チェックポイント。** `shard/{E}/{i}` を i ごとに集める（§4.7）。

**緊急分割は作らない。** 攻撃者はラベルから v を計算できないので 1 つのシャードだけを満杯にはできず、全部を埋めるには S_E 倍の PoW が要る。余裕 4 倍で決め、CheckpointDO の size ログ（いま 4 GiB）を 2 GiB からの警告にして、次の era の `S` を上げる運用にする。§14 の `MOVED`・凍結範囲は保留。もし要るなら「親シャードは時刻 t_s 以降その範囲の put を拒み、Worker は `t_s + SKEW` 以降 親.get → 子.put の 2 段で書く」で CAS を保てる（SKEW の範囲で親の拒否が先に立つ）。

**封印した era を R2 へ。** `end(E) + SKEW` で封印されたシャードは、アラームで（1 回 15 分以内、進み具合を meta に保存しながら）R2 に書き出す：

```
seal/{E}/{i}/rows        行を (t, label) 順に並べた 1 本のファイル = feed のページ列そのもの（§10.9 のバッチ形式）
seal/{E}/{i}/idx1        1 024 行ごとに先頭の (v, label) と idx2 内のオフセット（2 000 万行で約 600 KB）
seal/{E}/{i}/idx2        (v, label) 昇順の全行について (rows 内オフセット, t, cls)：28 B/行
seal/{E}/{i}/manifest    s_E、kroute_E（§14 のとおりここで公開。kcommit_E と照合できる）、バッチ一覧 (t, n, root, head)、
                         feed ページの境界オフセット、最終 head、各ファイルの SHA-256、SRV_SK の署名
```

- 書き出しが終わり、Worker が manifest を検証して読めることを確かめたら、ShardDO は `deleteAll()` して空になる（名前は残るが費用は消える）。行のコピーは 1 つだけ：`rows` は feed の形なので `/api/v2/feed/{E}/{i}` はそのまま R2 の Range から配り、点の検索は `idx1`（キャッシュ）→ `idx2` の 28 KB ブロック（Range、キャッシュ）→ `rows` の Range の 3 読みになる。exists モードの探査は `idx2` までで済む。manifest がある era は R2、ない era は DO、という判定を Worker が isolate ごとにキャッシュする。
- 封印した era の get は復元の探査とスクロールバックだけなので（追いつきは現在と直前の era）、遅延は許容できる。`MISS(sealed = 1)` は manifest が最終なので今までどおり最終。
- 費用：DO の SQLite 保存（$0.20/GB·月）から R2（$0.015/GB·月）へ。いま DO に残っている過去の era も同じ手順で移す。
- 段階を分けてもよい：先に本文だけ R2 へ移して索引は DO に残す（保存量の約 85 % が消える）、次に索引も R2 へ移して DO を空にする。

### 4.2 リアルタイム：`conn/v2/{c}` × C と `feed/v2/{f}` × F

stage 1 の RealtimeDO を「接続を持つ ConnDO」と「トピック → ConnDO の索引を持って配る FeedDO」に分ける（§14 の ConnDO / FeedDO）。

```
クライアント ═WS═ Worker ──▶ conn/v2/{c}          c = HMAC(k_conn, clientTag) mod C   ソケット・添付・RESUME リング・各上限（stage 1 の RealtimeDO と同じ）
put / sync ───── Worker ──▶ feed/v2/{f}.publish   f = HMAC(k_feed, topic) の上位ビット   メモリ上の topic → {c → 購読数}
                            feed ──▶ conn.deliver(rows)   購読している ConnDO にだけ転送 ──▶ ROWS / NOTE フレーム
```

- **ConnDO** は stage 1 の RealtimeDO からトピック索引の全体性を取ったもの。同じクライアント（タグ）のソケットは同じ ConnDO に集まるので、クライアントあたり 8 本の上限はそのまま数えられる。RESUME のリングと `boot` は ConnDO ごと。`ws-tag-key` は RealtimeDO の保存から Worker の秘密（`ROUTE_KEY` からの導出）に移す。
- **FeedDO** は保存を持たない。起動時（最初の要求、または退避からの復帰）に、何かに答える前に全 ConnDO（c < C）から `topicsFor(j)` で購読を引き取るので、FeedDO の再起動で購読は失われない。ConnDO は、自分のソケット全体でそのトピックを持つものが初めて現れたとき・最後の 1 つが消えたときだけ `interest(c, added, removed)` を送り（同じ FeedDO への呼び出しは順番に 1 つずつ）、5 分ごとと失敗の後（1 秒から 60 秒まで倍々）には `replace(c, topics)` で全集合を送り直す。FeedDO は 15 分呼び出しの無い ConnDO の購読を捨てる。トピックはどこにも書かれない（§13.1）。規範は PROTOCOL.md §9.4。
- **publish** は Worker から f ごとに 1 RPC（1 つの put は普通 1 トピック）。FeedDO は行ごとに購読 ConnDO へ `deliver` する。配送の遅延は DO 2 段分（同じ地域なら数 ms、違えば数十 ms）。
- **上限**：ソケット C × 2 万、対 C × 25 万、publish F × 1 000/秒。C と F は配備変数で、変えても再接続（1 時間以内）で収束する。
- **費用**：定期の `replace` は「トピックを持つ ConnDO × その FeedDO」の数を 5 分で割った分だけで、無負荷ではゼロ。C = F = 64 でも最大約 14 req/s。FeedDO の起動は C 回の RPC。

### 4.3 受信箱：バケット β_E、鍵付きのバケット写像、通知トピック

**なぜここだけ難しいか。** 招待はタグなしの試行復号で見つけるので、読み手のコストは「自分が読むバケットの招待数」に比例する。全員が 1 つのバケットを読む限り（β = 0）、匿名集合は全ユーザーだがコストは O(全招待)。匿名集合の大きさ K を固定すれば読み手のコストは一定になる（全招待数 × K / N）。これは PIR や OMR なしには越えられない関係で、FMD（fuzzy message detection）のような古典暗号の検出タグは量子 P に受信者を明かす。

**提案。**

- `β_E = max(0, ⌊log2(N_E / K)⌋)`、`K = 2^14`（16 384 人）、`N_E` は `start(E) − SKEW` 時点の `dirmeta.users`。`INBOX_MAP` に era ごと書き（`SHARD_MAP` と同形）、`/api/v2/era/{E}` に出す。いまの規模では β = 0 のままで、何も変わらない。
- バケット g は `inbox/v2/{E}/{g}`。1 日の上限（2 000）はバケットごと。読み手は自分のバケットだけ読み、カーソルは `(E, g, rel)`。
- **受信者のバケットの決め方（2 案）**
  - **案 A**（§14 の案）：`g = hpre(受信者) の上位 β_E ビット`。公開なので P は「このプレフィックスの約 K 人のうちの 1 人」まで分かる。実装は最も単純。
  - **案 B**（推奨）：`g = HMAC(kbucket_E, enc("segv.sh/v2/inbox/bucket", u16 β_E, u32 x)) mod 2^β_E`、`x = hpre の上位 pb_E ビット`、`pb_E = β_E + 5`（入力プレフィックスあたり K / 32 = 512 人）。`kbucket_E` は era ごとの Worker 秘密（`ROUTE_KEY` から導出）で、公開しない。Worker は `GET /api/v2/dir/h/{p}/{x}` の応答に、その x の上位 pb_E ビットから計算した `E_now` と `E_now + 1` のバケットを添える（クライアントの p ≈ log2(N / 64) に対して pb_E = log2(32 N / K) なので、K = 2^14 なら 4 ビットの余裕があり、ふつう `p ≥ pb_E`。足りないときだけ pb_E ビットでバケットを別に問い合わせる）。読み手は自分の `GET /api/v2/dir/uid/{uid}` の応答から自分のバケットを得る。
    - O に新しく漏れるものはない（送信者のプレフィックス検索も、読み手の自分の uid 検索も、いまある）。
    - 受動的な P（保存された全データを持つ者、将来の量子計算機を含む）にはバケットとユーザーの対応が計算できないので、受信者の匿名性は今と同じ「全ユーザーの中の 1 人」のまま。
    - 能動的な P\*（アカウントを作り、自分宛ての招待でバケットを観測する）には、観測した入力プレフィックスの分だけ案 A に近づき、下限は K。全部を写すには era ごとに `2^pb_E = 32 N / K` 個のアカウント（N = 100 万で約 2 000）と、それだけの公開の dirlog の行が要る。
    - `kbucket_E` は era E が保持期間（4 era）を出たら Worker の秘密から消す。O の鍵が後で漏れても過去の対応は復元できない。
- **ポーリングをやめる**（PROTOCOL.md §9.3・§10.8・§11.5 に規範を書いた）。バケットごとに公開の通知トピック `Tinbox(E, g) = t16(H(enc("segv.sh/v2/topic/inbox", u16 E, u32 g)))` を置く。InboxDO は、行の入ったスロットが閉じて `SKEW + 1` 秒たつとアラームで、FeedDO 経由で `INBOX = 0x85 | u16 E | u32 g | u32 rel` を配る（本文なし、保存なし、リングにも入れない）。投稿時刻ではなくスロット境界で出すので、ジッタで隠した投稿時刻は漏れない。1 回のアラームで閉じたスロットが複数あっても通知は 1 つで、`rel` は最新のもの。Worker の受信箱キャッシュはスロットの終わりで切れるので、通知を受けて読めば閉じたスロットが見える。クライアントは E_now − 1..E_now + 1 のバケットの通知を購読し、通知が来たら読む（読んだ `closed < rel` なら Δin 後にもう一度）。安全網として追いつき時の読み取り（接続中は 5 分に 1 回、切断中は 10 秒に 1 回、§11.6）は残す。O から見える新情報はない（購読者のバケットは、O が知っている読み手のプレフィックスの関数。stage 1 では全員が同じバケット 0）。P に見えるのも、読めば分かる「このスロットに行がある」だけ。

### 4.4 BlobReg：`blobreg/v2/{j}` × B

- `j = HMAC(kblob, id) の上位 b ビット`（`kblob` は `ROUTE_KEY` から導出。id は内容ハッシュなので鍵なしだと 2^b 回の試行で狙ったシャードに載せられる）。B は配備で 1 度決めて固定（既定 64 = 約 64 000 req/s）。同じ id の `register` と `meta` は同じシャードに行くので、§6.4(g) の最終性（MISS が報告した now より後の登録は `t` がそれ以上）はシャードごとの `hw` でそのまま成り立つ。
- 移行：いまの 1 つの `blobreg/v2` から `(id, size, t)` を 1 回コピーする（内部 RPC を 1 つ足す。登録あたり数十バイト）。旧オブジェクトは監査のため読み取り専用で残す。
- チェックポイント：B 個の head を `blobreg = H(enc("segv.sh/v2/blobreg/all", u32 hour, head_0 ‖ … ‖ head_{B−1}))` の 1 項目にまとめ、1 時間に 1 回だけ更新する。`hour` を混ぜるので登録がなくても値が変わり、P は「この 1 時間に登録があったか」も分からなくなる（今より狭い）。各シャードの head はシャードと CheckpointDO の保存に残し、将来ミラーフィード（§14）を作るときに公開の形を決める。

### 4.5 Push：保存は KV に、DO はメモリだけ、送るのは Worker

**stage 1 の PushDO が重い理由。** 1 つのオブジェクトに、保存（登録）・索引（呼び鈴 → 端末）・合流の窓・5 秒の保留と既読の印による取り消し・送信・期限切れの掃除がすべて入っている。しかも保存が DO の SQLite なので、基盤が 30 日持つ時点復元の履歴に変更の時刻が残らないよう、変更は日次パスでまとめて書き、控えを 1 分に 1 行の固定長で書き、アラームを 10 秒ごとに回している。その結果、利用者がゼロでも 1 日 8 640 回のアラームと 1 440 行の書き込みがあり、登録は約 15 件/分で BUSY、送信は約 50 push/秒、端末は 10 万まで、日次パスは 1 回 2 万行。これを K 個に分けても、固定費が K 倍になるだけで構造は変わらない。

**本当に共有状態が要るものは 3 つだけ。**

| 必要なもの                               | 性質                                              | 置き場       |
| ---------------------------------------- | ------------------------------------------------- | ------------ |
| (a) 呼び鈴 → 端末（封をした宛先と鍵）    | 永続。ring のたびに引く。変わるのは登録のときだけ | ストア（KV） |
| (b) 端末ごとの「1 分に 1 push」の窓      | 一時的。長くて 1 分                               | メモリ       |
| (c) 5 秒の保留と、既読の印による取り消し | 一時的。1 秒未満の鮮度が要る                      | メモリ       |

- (a) を DO に置く理由は無い。KV に即時に書けばよい。KV には時点復元も版管理も無い（この前提は明記する）ので、書く時刻を隠すための控えも日次パスも要らず、保存されるものは §9.8 の列挙と同じ（封をした宛先と鍵、鍵付きハッシュ、日）。期限切れは `day` を見る掃除で落とす。
- (b) と (c) にはアカウントの端末をまたぐ共有メモリが要る。Cloudflare でそれを最も安く与えるのは DO のメモリ（1 リクエスト $0.15/M）で、KV の書き込み（$5/M）で代用すると 1 push あたり 30 倍の費用になり、Queues のバッチで代用すると既読の取り消しが確率的になる。だから **DO は残すが、保存もアラームも持たないメモリだけのオブジェクト**にする。オブジェクトが消えて失うのは窓と保留だけで、stage 1 が再起動で失うものと同じ。

**案 B-1（推奨。API はそのまま）**

```
登録  POST push/sub ──▶ Worker ──▶ bell/v2/{j}.sub          呼び鈴ごとのシャード：メモリを更新し、KV "bell/<tk>" を書く
                                 └─▶ KV "ep/<ep>" = {bells, day}  1 日 1 回の更新で足りる
ring  POST ring ─────▶ Worker ──▶ bell/v2/{j}.lookup(bells) → (ep, box, Qh) …
                                 ──▶ quiet/v2/{k}.arm(Qh, 端末, row)          k = Qh の上位ビット
                      waitUntil で 5 秒 + ジッター待つ ──▶ quiet.due(Qh) → 送る端末と box
                      Worker が push サービスへ送る（VAPID / APNs / FCM）。410 なら KV から消す
seen  POST seen ─────▶ Worker ──▶ quiet/v2/{k}.seen(Qh, rows)                 メモリに 120 秒
```

- **KV `PUSH_KV`**：`bell/<tk>` → 最大 8 件の `(ep, box, Qh)`。書き手はその呼び鈴の bell シャードだけで、順番に書くので競合せず、1 鍵 1 秒 1 書き込みの制限にも当たらない。`ep/<ep>` → `{bells の tk, day}`（掃除と、1 日 1 回の更新のため）。`quiet/<Qh>` → 同期メモを受ける端末の `(ep, box)`（書き手は quiet シャード）。値はすべて `PUSH_KEY` で封をしたまま。読みはエッジで効く。
- **`bell/v2/{j}`（メモリだけ）**：呼び鈴 → 端末の索引。知らない呼び鈴に初めて触れたとき KV から読む（遅延再構築）。登録はここが単一の書き手として KV に反映する。「8 枠、先着」は今のまま。
- **`quiet/v2/{k}`（メモリだけ）**：アカウント（静けさタグの鍵付きハッシュ Qh）ごとに、端末の `last` / `due` / `rang` / `rows` と既読の印。`arm` で保留を作り、`due` で窓と印を見て「いま送る端末」を返す。アカウントの端末は同じ Qh なので必ず同じシャードに集まり、「1 分に 1 push」と既読の取り消しは stage 1 と同じ厳密さで守れる。
- **送るのは Worker**：VAPID の JWT は isolate ごとに 12 時間キャッシュ、暗号化は 1 push 1 ms ほど。水平に伸びるので 50 push/秒の上限は消える。ring を受けた Worker が `waitUntil` で保留（5 秒 + 最大 Δ）を待ち、`due` を呼んで送る。窓の中に来た ring の分（最長 60 秒先）は `waitUntil` の 30 秒に収まらないので、Queues の遅延メッセージ（`delaySeconds` = 残り時間、中身は Qh だけ）で消費側の Worker が `due` を呼ぶ。アラームは要らない。
- **掃除**：Cron Trigger の Worker が 1 日 1 回 `ep/` を list し、30 日更新の無い端末を bell シャード経由で消す。日次パスの代わりで、DO の中では何も回らない。
- **上限**：`PUSH_MAX_SUBS`・`PUSH_DAY_SUBS`・BUSY は消える（控えが無いので）。残るのは PoW、IP ごとのレート制限、呼び鈴 8 枠、端末 256 呼び鈴。
- **費用**：固定費ゼロ。ring 1 回 ≈ DO の RPC 1 回 + 受信アカウント数 × 2 回（$0.15/M）。KV の読みはシャードの再構築のときだけ。登録 1 回 ≈ 呼び鈴の数だけ KV 書き（$5/M）。100 万端末が 1 日 1 回更新し、1 日 1 000 万 ring なら 1 日 $20〜30 の桁。
- **移行**：旧 PushDO の `sub` / `tok` を 1 回読んで KV と索引に入れる（封は `PUSH_KEY` のまま）。クライアントの変更は無い。

**案 B-2（次の段階。呼び鈴を持ち主が選ぶ）**：§14 の「持ち主が選ぶ呼び鈴」を端末スロットつきにする。アカウントの端末は自分のレーンで 0〜7 のスロットを取り（行と同じく CONFLICT で決まる）、端末ごとの秘密 `s` から `bell = H(s)` を作り、会話のメンバーには会話の中の記録で `bell` の一覧を伝える。登録では持ち主の端末だけが `bell/<tk>` を書く（競合しない）ので bell シャードも索引も要らず、他人の呼び鈴の枠を取る攻撃（§0.4）も消える。呼び鈴を付け替えるのはメンバーを外したときだけで、エポック変更のたびではない。quiet シャードと Worker 送信は B-1 のまま。

**案 C（DO を完全になくす）**：B-2 に加えて、保留は `waitUntil` の 5 秒だけ、窓は Cache API（colo ごと。送信者の colo が違えば重なる）、既読の取り消しは送る前ではなく届いた後（ネイティブアプリは静かなプッシュで消す。Web Push は表示したまま）、窓の中の ring は Queues で遅らせる。失うのは「送る前の既読の取り消し」と窓の厳密さで、§13.4 の「端末あたり 1 分に 1 回」が「送信者の colo ごとに 1 分に 1 回」になり、N と M への漏れが少し増える。

**秘匿性の監査**（B-1 / B-2）：保存は §9.8 の列挙と同じ列を KV に即時に書く。履歴の懸念は KV に時点復元が無いことで消える。ring と seen は今までどおり何も書かない（Queues のメッセージだけは数十秒ストアに乗るので、Qh の鍵付きハッシュだけを載せ、行も呼び鈴も載せない）。N が見るもの（固定長、1 分に 1 回、5 秒以上の遅れ）と O が見るものは不変。

### 4.6 ディレクトリ：`dirseq/v2` と D1 の分割

- **書き込み**：`dirseq/v2` という 1 つの DO が dirlog の seq を払い出し、鎖 `h` を計算し、20 ms ほど待ってまとめた 1 回の D1 `batch()` で書く。楽観的リトライ（§9.6）は消える。1 000 RPC/秒 × バッチなので登録のバーストに耐える。D1 が落ちていれば今までどおり 503。D1 が正であることは変えず、DO は起動時に D1 の head を読み直す。
- **読み取り**：D1 の読み取りレプリカ（Sessions API）。`no-store` の規則は変えない（「新しい完全な答え」の意味を保つため）。
- **容量**：10 GB は約 150 万アカウント。超える前に `upre` の上位ビットで K 本の D1 に分け、dirlog は専用の 1 本に置く。uid 検索は 1 本、ハンドルのプレフィックス検索は K 本に投げて uid 文字列順にマージ（応答の規則は不変）。複数 D1 への書き込みは原子的でないので、`dirseq/v2` 自身の SQLite を先行ログにして冪等に再実行する。

### 4.7 チェックポイント

- 収集先が `S_E + S_{E−1}` のシャード、`2^{β_E} + 2^{β_{E−1}}` のバケット、blobreg（毎時）、dirlog になる。並列度 32 で引く（S = 256、β = 6 でも約 600 RPC で、10 秒に収まる）。足りなくなれば、シャードがバッチを閉じたときに head を push する形に変える。
- `heads` の列は毎分数十 KB になりうるので、DO には `(q, sec, hd, C, sig)` だけ保存し、列は R2 の `ckpt/{q}` に不変で置く（`/ckpt/{q}` はそこから配り、`/ckpt/latest` はメモリの最新の列）。

### 4.8 Worker と乱用対策

- Worker は無状態で、やることは今と同じ（ホスト・レート制限・PoW・経路決め・受領証の署名・publish）。1 リクエストで複数シャードに並列 RPC するだけ。
- レート制限（IP 単位）と PoW は変えない。§14 の匿名トークン（VOPRF）は独立に進められる。分割によって、受信箱と行の上限を「攻撃者が全部埋める費用」は 2^β 倍・S_E 倍になる。

## 7. 移行の順序

当たる順に並べる。どれも前の項目に依存しない。

1. **リアルタイムの分割**（ConnDO / FeedDO。PROTOCOL.md §9.4 に規範を書いた）：最初に当たる上限（約 1 万タブ）。状態がないので無停止で切り替わる。
2. **受信箱の通知トピック**（PROTOCOL.md §9.3・§10.8・§11.5 に規範を書いた）：ポーリングの費用が最大の固定費。クライアントは購読と、追いつき時だけの読み取りに変わった。
3. **S_E > 1**：次の era から。`SHARD_MAP` と era 情報、チェックポイントの収集、feed の i。
4. **封印 era の R2 化**と DO の削除：費用。過去の era にも適用。
5. **BlobReg と dirseq**：コピー 1 回と、D1 への書き手の一本化。
6. **Push を KV + メモリだけの DO + Worker 送信に**（案 B-1。PROTOCOL.md §9.8 に規範を書いた）：固定費も消える。
7. **受信箱バケット**：N ≥ 2K（約 3 万人）になる era から。案 A / B はここまでに決める（決めておけば β = 0 のまま先に実装できる）。
8. **D1 の分割**：100 万アカウントの前。

## 8. 採らなかった案

- **Workers の外（Postgres + Redis / Kafka）へ出す**：必要な原始操作は「鍵ごとに 1 つの直列化された書き手と保存」で、それは Durable Object そのもの。移して得るのは 10 GB/オブジェクトの制限の回避だけで、それは分割と R2 化で得られる。運用の負担だけ増える。
- **行を D1 や KV に置く**：D1 は書き手が 1 つで 10 GB、アラームがない。KV は結果整合なので「最初の書き込みが勝つ」が作れない。
- **R2 の条件付き PUT だけで create-only にする**：`t` を割り当てる直列化（`t` が閉じたバッチに落ちない、MISS の後の登録は `hw` 以上）が R2 にはない。R2 は封印後の置き場。
- **Queues で fan-out**：秒単位の遅延。
- **クライアントがトピックのシャードごとにソケットを開く**：最大 256 トピックが F 本の接続に散る。モバイルで不可。ConnDO が吸収する。
- **受信箱に検出タグ（FMD など）を付ける**：古典暗号なので量子 P に受信者を明かす。耐量子のタグは 1 KB 級で、ダウンロード量が減らない。
- **受信箱を era の途中で分割する**：β は era 内で固定しないと読み手のカーソルが壊れる。

## 9. 決めてもらう点

1. 受信箱の案 A / B と K の値（§4.3）。推奨は案 B、K = 2^14。
2. BlobReg の毎時の項目を「常に変わる」にするか（P から「登録があったか」が消える。透明性より秘匿を取る）。
3. S_E の決め方を運用（`SHARD_MAP`）にとどめるか、前の era の実績から自動にするか。
4. FeedDO への呼び出しが失敗している間の取りこぼし（次の再送まで、最長 60 秒。5 分の追いつきで回復）を許容するか。
5. Push は案 B-1 で決まり（§4.5、PROTOCOL.md §9.8）。残るのは B-2（持ち主が選ぶ呼び鈴で索引の DO も無くす）に進むかどうか。
